# B2B UI/UX Reference

这是一份面向企业管理、运营后台、专业工作台和数据密集型扩展的**可选设计资源**。它用于帮助 Agent 识别用户可能期待的产品方向，提炼客户管理扩展中经过验证的设计思路；它不是默认模板，也不是所有扩展都必须遵守的页面结构。

## 何时考虑加载

当需求包含以下信号时，考虑读取本资源：

- 企业管理、客户管理、项目管理、组织、权限、审批、配置或运营后台
- 用户需要长期、重复、专业地处理业务数据
- 需求包含搜索、筛选、排序、分页、批量操作、状态追踪或数据对比
- 用户强调工作台、控制台、效率、信息密度或桌面端专业操作
- 页面需要同时服务桌面端和移动端的不同任务

以下场景通常不需要加载本资源，除非用户明确要求企业后台风格：小游戏、创作工具、媒体工具、可视化画布、单次向导和强品牌表达页面。

## 使用方式

先判断 B2B 范式与当前需求的匹配度：

- **匹配度高**：需求明显是企业业务模块，且涉及持续数据处理、状态管理或多角色协作。可以直接采用合适的范式，并在实现中说明关键取舍。
- **匹配度中等**：只有部分信号符合，或页面既有业务操作又有强品牌/创作属性。选取局部模式，不要整套套用。
- **匹配度不确定**：页面形态和目标用户不清晰，或 B2B 风格会明显影响视觉方向。向用户询问，例如“这个页面更偏专业管理工作台，还是偏轻量操作/品牌体验？”
- **匹配度低**：不要因为这是扩展就套用后台模板，按业务自身的任务、内容和设备场景设计。

不要为了使用本资源而要求用户安装浏览器、截图工具或其他额外工具。它是设计判断资料，不是新增工具链。

## 可选范式

### 1. 模块首页先交付价值

将扩展 Sidebar 视为模块首页或移动 App 的 Tab 页面。用户打开后应立即看到与当前模块最相关的内容，例如：

- 核心指标和趋势摘要
- 待处理事项和下一步行动
- 高频功能入口
- 最近活动或少量高价值数据
- 状态分布、风险提示或需要关注的异常

不要把首页退化成只有一个“打开列表”按钮的导航壳。也不要机械地把所有数据都塞进首页；首页只承载最有价值、最适合快速扫描的内容。

### 2. 持续处理进入工作区

当用户需要连续浏览、搜索、筛选、排序、分页、比较、统计或批量处理时，提供独立的 Editor 或等价工作区。让用户能够：

- 保留筛选、排序、分页和选中上下文
- 直接完成批量操作，不必逐条打开详情
- 在高信息密度和易扫描之间选择合适的呈现方式
- 从列表进入详情后可快速返回原任务位置

表格、卡片、分组列表、看板、时间线或其他结构都可以，只根据任务选择，不把“卡片 + 表格”当成固定组合。

### 3. 详情与编辑保持上下文

单条记录的详情、关联信息、生命周期和中等复杂编辑，通常可以使用 Drawer，以便用户保留当前列表上下文。字段少、步骤短、需要立即确认的操作可以使用 Dialog；多步骤、长时间编辑或独立工作流可以升级为 Editor。

这是帮助选择容器的判断方式，不是组件强制清单。优先使用 SDK 提供的 Dialog、Drawer、Sheet 和焦点管理能力，业务只实现业务内容和状态。

### 4. 桌面端与移动端各自服务任务

办公类扩展需要判断设备上的主要任务，而不是只缩小桌面布局：

- 桌面端可强调比较、批量处理、常驻筛选和较高信息密度
- 移动端可强调快速查看、触控、单列层级、关键字段和即时行动
- 相同数据可以使用表格、卡片或分组列表的不同呈现，不要求 DOM 和视觉结构完全相同
- 筛选可以在桌面端常驻，在移动端收进 Drawer；详情和编辑也应保持容易返回
- 重要操作、状态反馈和错误恢复在两端都必须可达

### 5. 状态、待办和行动闭环

B2B 页面通常不仅展示数据，还要帮助用户完成下一步行动。根据业务选择：

- 让状态在列表、详情和首页摘要中保持一致
- 将待办、异常、加急或阻塞项放在用户容易发现的位置
- 为空状态提供下一步 CTA，为加载提供稳定骨架，为失败提供重试或明确处理方式
- 危险操作使用清晰的确认流程，并说明影响范围
- 避免仅用颜色表达状态，同时提供文字、图标或结构线索

## 与主题系统协作

B2B 范式不会替代主题规范。使用 Tailwind 时仍必须使用 Workbench 的语义主题 token，例如 `bg-background`、`text-foreground`、`bg-card`、`border-border` 和 `text-muted-foreground`。本资源不提供固定品牌色、固定圆角或固定组件配色。

## 采用前的自检

在采用某个范式前，回答：

1. 用户打开页面最想立即知道什么或完成什么？
2. 哪些任务是高频、持续、需要比较或批量处理的？
3. 哪些信息应该留在模块首页，哪些信息需要进入独立工作区？
4. 详情、编辑、筛选和确认分别需要多大上下文和操作空间？
5. 桌面端和移动端的主要任务是否不同？
6. 这个范式是否服务当前需求，还是只是看起来像熟悉的后台模板？

回答不清晰时，保留设计选择并询问用户，不要把本资源升级成硬性约束。
