# 立项前拷问审查（Pre-Development Interrogation）

## 0. 定位与触发时机

**触发时机**：接到一个"把某个业务系统／业务模块搬进工作台做成扩展"的需求之后，**写第一行前端代码之前**。

**角色**：我们站**平台方 ＝ 甲方**位，要求最高，对需求方（业务方，或我们自己的业务模块）发起提问。

**本质**：把 fresh-eyes 审查**提前到立项之前**，且把审查对象从「代码对不对」换成
**「这个功能该不该存在／缺什么才能成立／代价多大」**。

**为什么不能跳过**：直接进入界面设计，等于用「界面能不能做得好玩」替换了「产品该不该这么做」。
界面设计是**收敛**动作（在既定范围里选方案），立项前审查是**发散 + 证伪**动作（推翻或重划范围）。
顺序颠倒后，方案越精致，错得越难改。

---

## 1. 输入：先读，读完再提问

| 序 | 输入 | 为什么要读 | 具体读什么 |
|---|---|---|---|
| 1 | 业务／需求文档 | 知道对方**想要什么** | PRD、业务流程图、设计稿、验收标准、术语表 |
| 2 | **已有后端代码（最重要，不可跳过）** | 知道**事实是什么** | 实体／表结构、字段类型与注释、枚举取值、**索引**、接口 DTO、校验规则、状态机 |
| 3 | 现有前端（若有） | 知道**已经做到哪一步** | 页面结构、交互流、**哪些字段真的被渲染了** |
| 4 | 平台契约（UI-CONTRACT） | 知道**我们的底线** | §7 容器语义与首屏价值、§5 质量基线、§6 样式技术路线 |

### 为什么后端代码排第二，且不可跳过

1. **文档会过期、会写错，代码不会。** PRD 是**意图**，实体是**事实**。两者不一致时以代码为准 ——
   并且**这处不一致本身就是一条质疑**，要写进报告（例：前端注释写「1 需求下单，2 预约下单」，
   后端实体写「1预约下单 2需求下单」，正好相反）。
2. **字段反推意图**：表里在累积什么字段，说明业务真正在关心什么。
   **字段存在而没有任何界面渲染它 = 已经漏掉的信息**，这是最便宜的需求来源。
3. **索引反推查询**：索引形状 = 「曾经有人认真想过这个查询」的证据。
   例如联合索引 `(tenantId, productId, mainStatus, createTime)` 说明
   「按产品看订单状态 + 时间分布」是被规划过的场景，只是前端没做 —— 比问 PM 快。
4. **注释反推边界**：实体注释常写着「不在订单展示」「平台后台可手工维护」「与派单动作解耦」
   这类**业务约定**，是判断某字段能否上界面的关键依据。
5. **枚举反推完整流程**：主状态枚举（如 11 个状态）本身就是业务生命周期的权威定义，
   可直接推导漏斗与明细维度，不必等业务方口述。

## 2. 五个拷问（逐条必须带证据）

> **纪律：任何「我认为不合适」必须附文件 / 行号 / 字段名 / 集合表达式。
> 没有证据的意见不进报告。**
> 这是本审查**唯一**的防走场机制 —— 打钩式检查表必然退化成走过场。

| # | 拷问 | 不合格的样子 |
|---|---|---|
| Q1 | **该不该存在**：这一节／这个功能的数据集，谓词是什么？ | 谓词是「全部」或「前 N 条」—— 见 UI-CONTRACT §7.7 四问 |
| Q2 | **有没有意义**：用户看完这条，下一个动作是什么？ | 绕回原点；或答不出动作 |
| Q3 | **够不够成立**：要成立，**缺什么**（字段／模型／接口／写路径）？ | 只说「能做」，不说「数据从哪来」 |
| Q4 | **是不是真的**：这个字段有没有**写入路径**？（谁写、何时写、历史数据怎么办） | 字段存在但没人写 → 展示出来是**假数据** |
| Q5 | **代价多大**：只增不改能解决吗？ | 一上来就要改现有契约／动存量数据 |

Q1 / Q2 是**意义层**，Q3 / Q4 是**可行性层**，Q5 是**代价层**。三层都过才有立项资格。

---

## 3. 产出：三张清单（不是一张）

| 清单 | 内容 | 交谁 |
|---|---|---|
| **质疑清单** | 现状哪里不成立 + 证据 + 建议改法 | 交需求方确认（含「我们更建议 X」的意见） |
| **缺口清单** | 要成立必须补的字段／模型／接口／写路径 | 按 §4 分级 |
| **增量清单** | 还能做什么（超出原始需求的更多需求） | 按 §4 分级，交需求方挑选 |

**「提意见」与「挖需求」就落在后两张清单上** —— 这也是本审查相对普通需求评审的增量：
不只回答「你要的能不能做」，还回答「你要的里哪些不成立」「你没要但值得要的有哪些」。

---

## 4. 成本分级 —— 「不过分」的可判定边界

需求方说「不过分就好」时，**不能靠感觉**。用三条闸门：

| 档 | 判据 | 处置 |
|---|---|---|
| **A · 直接做** | 数据已存在**且**接口已返回，只是没被消费；不改契约、不改表 | 进本次范围 |
| **B · 立需求排期** | 数据齐全，需新增**只读**聚合接口 | 本次可先不做，**登记需求并排期** |
| **C · 需产品／财务定义** | 需改数据模型，或存在业务口径争议 | **不进本次**，先出定义文档 |

**「不过分」的操作定义 = A 档 ＋ 不改现有契约 ＋ 不动存量数据 ＋ 可回退。**

⚠️ 落到 B / C 档不等于「不做」，而是「**先记账再排期**」。
把 C 档混进本次范围是最典型的越界 —— 那时写出来的不是功能，是**口径未定义的假指标**。

---

## 5. 三条纪律（防止这套方法论被做坏）

1. **证据纪律**：见 §2 开头。无证据的意见是噪声，不进报告。
2. **写路径纪律**：**没有写入路径的字段，不许进 UI**。
   Agent 时代「缺什么补什么」确实便宜 —— 但**便宜的是加一列 DDL，贵的是「谁来填、填错谁负责、历史数据怎么补」**。
   先验证写路径，**再**设计界面。
3. **双向纪律**：我们拷问需求方，**需求方也可以反问我们的契约**。
   我们自己也在违规先例名单里（曾自定 21 个 `--crm-*` 私有 token 写进设计规范）。
   单向拷问 = 甲方拍脑袋。

---

## 6. 角色边界（最容易搞错的一点）

- 我们站甲方位，管的是三件事：**合规**（是否守平台契约）、**可维护**（结构／成本／可回退）、
  **一致**（跨模块体验是否统一）。
- **但「产品意义」的判定权在业务方 / 最终用户，不在我们。**
- 平台以「大老板」自居去替业务方定义产品意义，产出会是**平台自嗨的扩展** ——
  好看、合规、跨模块一致，**但没人用**。
- 正确姿势：**我们负责「能不能、值不值、代价多大」，业务方负责「要不要」。**
  有分歧时，出证据 + 出选项 + 给出我们的建议，**但不替对方拍板**。

---

## 7. 通过与不通过

**通过条件**（全部满足）：

- [ ] 三张清单齐备，且**每一条都带证据**（文件／行号／字段名／集合表达式）
- [ ] C 档项已明确排除并**登记**（不是悄悄砍掉）
- [ ] Q4 写路径已验证（或已列入缺口清单）
- [ ] 需求方对 A 档范围**明确点头**

**不通过**（不允许进入设计阶段）：

- 无证据的「我觉得」
- 缺口未识别（"能做"但没说数据从哪来）
- 写路径未验证
- C 档混进本次范围

**通过后** → 才进入 UI-CONTRACT §7 的容器设计与实现，并按 §7.7 逐节自查。
