# 立项前拷问审查（Pre-Development Interrogation）

## 0. 定位与触发时机

**触发时机**：接到一个"把某个业务系统／业务模块搬进工作台做成扩展"的需求之后，**写第一行前端代码之前**。

**角色**：我们站**平台方 ＝ 甲方**位，要求最高，对需求方（业务方，或我们自己的业务模块）发起提问。

**本质**：把 fresh-eyes 审查**提前到立项之前**，且把审查对象从「代码对不对」换成
**「这个功能该不该存在／缺什么才能成立／代价多大」**。

**为什么不能跳过**：直接进入界面设计，等于用「界面能不能做得好玩」替换了「产品该不该这么做」。
界面设计是**收敛**动作（在既定范围里选方案），立项前审查是**发散 + 证伪**动作（推翻或重划范围）。
顺序颠倒后，方案越精致，错得越难改。

## 1. 输入：先读，读完再提问

| 序 | 输入 | 为什么要读 | 具体读什么 |
|---|---|---|---|
| **0** | **决策台账 `NN/09-决策记录.md`（最先读，必读）** | 知道**已经拍板了什么、已经决定不做什么** —— 这类信息**代码里根本没有**，也永远反推不出来 | 全部 `D0xx` 条目。文首使用规则原话：「与其他文档冲突时，**以本文档为准**」 |
| **1** | **业务／需求文档树** | 知道对方**想要什么**，以及设计走到了哪一级 | **必须定位到文档树，不是产品说明书。** 本项目在 `server/docs/sci开发文档/<域>/`：`00-域总览与开发顺序`、`01~12` 各模块（产品/下单/状态机/交易底座/…）、`09-决策记录`；外加 `平台架构域/01-平台开发约定摘要.md`（模块手续 Checklist、文档状态五级制、字段字典、模块归属与 scope 拆分）。**`workbench/PRODUCT.md` 那类产品说明不能顶替这里** |
| 2 | 已有后端代码 | 知道**事实是什么**（≠ 想要什么） | 实体／表结构、字段类型与注释、枚举取值、**索引**、接口 DTO、校验规则、状态机 |
| 3 | 现有前端（若有） | 知道**已经做到哪一步** | 页面结构、交互流、**哪些字段真的被渲染了** |
| 4 | 平台契约（UI-CONTRACT + 平台架构约定） | 知道**我们的底线** | §7 容器语义与首屏价值、§5 质量基线、§6 样式技术路线；**以及决策台账里的技术选型类决策**（如 D069 扩展组件选型：SDK 优先 / 禁止原生 HTML 控件 / 缺口记录而非自研） |

### 1.1 三条硬规矩（这是本审查最容易失守的地方）

**规矩一：代码注释里的编号就是文档索引，必须逐个追到原文。**
实体与前端的注释里满是 `D018` / `D020` / `R25` / `04 §8` / `03 §三` / `定稿线A#9` 这类引用 ——
它们**不是装饰**，是**指向权威定义的路标**。追不到原文的编号，登记为「**编号悬空**」；
一个都不追，等于**承认自己没读需求**。

**规矩二：报告必须附「条款对照表」，否则不算读过。**
每一条结论后面标明引用来源（`D0xx` 或 `NN §x.x`）。写不出条款编号的结论，按 §2 的证据纪律**不进报告**。

**规矩三：必须先做「已拍板决策比对」。**
把本功能涉及的每个动作，逐条对照决策台账：**有没有一条 D0xx 已经拍过它？拍的是做、还是不做？**
本项目真实教训：设计"订单统计看板"，而 **D029 早已拍板「不做独立统计接口」**（统计诉求由订单列表检索满足）——
一条决策就把整个方案否掉了，而这个信息**只能从台账里得到**。

### 1.2 ⚠️ "以代码为准"的适用边界（我在这句话上栽过）

「文档会过期而代码不会，冲突时以代码为准」——**这句话只适用于这一类矛盾**：
*文档说 A、代码做 B，同一个事实有两种说法*。

它**不适用**于另外两类问题，这两类必须以**文档／台账**为准：

| 问题类型 | 例子 | 谁为准 |
|---|---|---|
| 「现在是什么」 | 字段有没有、枚举几个值、索引什么形状 | **代码**（代码是执行的真相） |
| 「**已经决定不做什么**」 | D029 不做独立统计接口；D058 供应商统计第一版只做筛选 | **决策台账**（代码里是"不存在"，无法反推"是被否掉的"） |
| 「**做这个算不算合规**」 | D069 禁止原生 HTML 控件、缺口要记录不要自研 | **平台约定 + 台账** |

**代码只能回答"现在是什么"，不能回答"为什么不是别的"。** 把"读了实体"当成"读懂了需求"，就是这次翻车的根因。

### 1.3 文档状态五级制（D061）—— 别把"设计定稿"读成"代码已实现"

文档头部的状态行是**五级**，且**绝大多数文档停留在第 2 级**：

| 级别 | 含义 |
|---|---|
| 1 业务决策已确认 | 规则拍板，设计未展开 |
| 2 **目标设计已确认** | 字段/状态/接口/事务边界定稿，**代码可能未实现** |
| 3 实现中 | 部分代码落地，契约不再大改 |
| 4 已实现待验收 | 代码+迁移完成，验收未走完 |
| 5 已验收 | 证据齐全 |

**代码进度不看状态行，看各文档内部的「待实现/待办」清单。**
不看这一条，就会把"设计已定稿"误判成"功能已存在"，进而对着不存在的功能设计界面。

### 为什么后端代码排第二，且不可跳过

1. **文档会过期、会写错，代码不会。** PRD 是**意图**，实体是**事实**。两者不一致时以代码为准 ——
   并且**这处不一致本身就是一条质疑**，要写进报告（例：前端注释写「1 需求下单，2 预约下单」，
   后端实体写「1预约下单 2需求下单」，正好相反）。
2. **字段反推意图**：表里在累积什么字段，说明业务真正在关心什么。
   **字段存在而没有任何界面渲染它 = 已经漏掉的信息**，这是最便宜的需求来源。
3. **索引反推查询**：索引形状 = 「曾经有人认真想过这个查询」的证据。
   例如联合索引 `(tenantId, productId, mainStatus, createTime)` 说明
   「按产品看订单状态 + 时间分布」是被规划过的场景，只是前端没做 —— 比问 PM 快。
4. **注释反推边界**：实体注释常写着「不在订单展示」「平台后台可手工维护」「与派单动作解耦」
   这类**业务约定**，是判断某字段能否上界面的关键依据。
5. **枚举反推完整流程**：主状态枚举（如 11 个状态）本身就是业务生命周期的权威定义，
   可直接推导漏斗与明细维度，不必等业务方口述。

## 2. 五个拷问（逐条必须带证据）

> **纪律：任何「我认为不合适」必须附文件 / 行号 / 字段名 / 集合表达式。
> 没有证据的意见不进报告。**
> 这是本审查**唯一**的防走场机制 —— 打钩式检查表必然退化成走过场。

| # | 拷问 | 不合格的样子 |
|---|---|---|
| Q1 | **该不该存在**：这一节／这个功能的数据集，谓词是什么？ | 谓词是「全部」或「前 N 条」—— 见 UI-CONTRACT §7.7 四问 |
| Q2 | **有没有意义**：用户看完这条，下一个动作是什么？ | 绕回原点；或答不出动作 |
| Q3 | **够不够成立**：要成立，**缺什么**（字段／模型／接口／写路径）？ | 只说「能做」，不说「数据从哪来」 |
| Q4 | **是不是真的**：字段有写入路径吗？**真的被写过吗**？（谁写、何时写、分布如何、历史数据怎么办） | 字段存在但没人写 → **假数据**；或只验到"能写"就收手 → **同样是假数据** |
| Q5 | **代价多大**：只增不改能解决吗？ | 一上来就要改现有契约／动存量数据 |

Q1 / Q2 是**意义层**，Q3 / Q4 是**可行性层**，Q5 是**代价层**。三层都过才有立项资格。

### Q1 之前还有第 0 问：主语是谁（模块归属）

在问「这一节的谓词是什么」之前，先确认**这个功能的主体属于哪个模块**。

**判据**：如果它的**主体（主语）是另一个模块的核心对象**，那它属于那个模块，不属于当前模块。
搬过来 = **模块归属越界** —— 两个模块抢同一件事，用户不知道该去哪个模块看，且两边会各自演化出不一致的口径。

**实例（本项目真实踩坑）**：给「服务项目管理」（`service-project`）设计"订单看板" ——
KPI 是订单总量 / 客单价 / 待处理，主体是「11 态状态分布 + 履约漏斗」。
但**订单**是 `order-management`（订单管理）的核心对象 ⇒ 越界，被需求方一句话点破。

**正确形态**：**本模块主体做主语，外部数据做它的属性**。
服务项目做主语、订单降为项目的一条属性（"这个项目揽到多少单"），
图表横轴是**项目**、纵轴是它的单量 —— 回答「哪些项目在真正做生意」，
而不是「订单整体怎么样」。

**一句话判据：主语错，页面再好看也是给别人写的。**

### 第 0 问的续问：外来数据以什么身份进来

确认"主语是本模块"之后，还要问：**那个外部对象的数据，以什么身份出现在本模块？**
只有两种合法身份：

| 身份 | 形态 | 例 |
|---|---|---|
| **谓词** | 变成一条**待办 / 筛选条件** | `已启用 ∧ 近 30 天订单数 = 0` → "4 个项目零订单，去排查" |
| **属性** | 变成主体的一条**列** | 服务项目的"累计单量 / 累计收入" |

**绝不合法的是第三种身份：看板。** 把外部对象的**整体分析**（状态分布、履约漏斗、趋势大盘）
搬进本模块，等于把它当主语用 —— 又绕回第 0 问的错误。

**同一份数据，两种身份并存是正常的**：订单数据进 `order-management`（它是主语）可以是看板；
进 `service-project`（它是修饰语）只能是谓词或属性。

**最后再对一次容器的表达层级**：
**主面板回答「我现在该做什么」**（状态 + 待办，一屏给结论与入口）；
**工作区回答「这件事具体怎么样」**（表格 + 图表 + 筛选，过程与工具）。
把工作区的东西塞进侧栏 —— 在 360px 宽里立不住，在移动端 30% 抽屉档更会碎成残骸。

## 3. 产出：三张清单（不是一张）

| 清单 | 内容 | 交谁 |
|---|---|---|
| **质疑清单** | 现状哪里不成立 + 证据 + 建议改法 | 交需求方确认（含「我们更建议 X」的意见） |
| **缺口清单** | 要成立必须补的字段／模型／接口／写路径 | 按 §4 分级 |
| **增量清单** | 还能做什么（超出原始需求的更多需求） | 按 §4 分级，交需求方挑选 |

**「提意见」与「挖需求」就落在后两张清单上** —— 这也是本审查相对普通需求评审的增量：
不只回答「你要的能不能做」，还回答「你要的里哪些不成立」「你没要但值得要的有哪些」。

## 4. 成本分级 —— 「不过分」的可判定边界

需求方说「不过分就好」时，**不能靠感觉**。用三条闸门：

| 档 | 判据 | 处置 |
|---|---|---|
| **A · 直接做** | 数据已存在**且**接口已返回，只是没被消费；不改契约、不改表 | 进本次范围 |
| **B · 立需求排期** | 数据齐全，需新增**只读**聚合接口 | 本次可先不做，**登记需求并排期** |
| **C · 需产品／财务定义** | 需改数据模型，或存在业务口径争议 | **不进本次**，先出定义文档 |

**「不过分」的操作定义 = A 档 ＋ 不改现有契约 ＋ 不动存量数据 ＋ 可回退。**

⚠️ 落到 B / C 档不等于「不做」，而是「**先记账再排期**」。
把 C 档混进本次范围是最典型的越界 —— 那时写出来的不是功能，是**口径未定义的假指标**。

## 5. 三条纪律（防止这套方法论被做坏）

1. **证据纪律**：见 §2 开头。无证据的意见是噪声，不进报告。
2. **数据真实性三级验证（缺一不可）**：一个字段要做进 UI，必须**逐级**验证，**不许跳级**：

   | 级 | 问 | 不通过的后果 | 怎么验 |
   |---|---|---|---|
   | L1 | **字段存在吗**（schema / 类型定义 / 接口返回里有没有） | 做不了 | 读实体 / DTO / 类型 |
   | L2 | **有写入路径吗**（谁写、什么时候写、租户能不能写） | 恒为默认值 → 假指标 | 读 DTO 校验 + service 落库逻辑 + 是否有 `delete` 剔除 |
   | L3 | ****有真实数据填充吗**（真的被写过吗、分布如何）** | **字段与写路径都齐备，但全表都是默认值 → 依然是假指标** | **查库看分布**（count / distinct / min / max / 非默认值占比） |

   ⚠️ **L2 通过不等于可用** —— 这是本项目真实踩过的坑：`satisfactionLevel` / `reservationCount`
   两级全过（DTO 可写、service 落库），但查库发现 **11 行全是列默认值（0 与 100）**，
   即"功能从未被使用"。若照 L2 结论直接上界面，展示的就是「预约 0 次 / 满意度 100 分」。
   **L2 只证明"能写"，L3 才证明"有内容"。**

   Agent 时代「缺什么补什么」确实便宜 —— 但**便宜的是加一列 DDL，贵的是「谁来填、填错谁负责、历史数据怎么补」**。
   先验证三级，**再**设计界面。
3. **双向纪律**：我们拷问需求方，**需求方也可以反问我们的契约**。
   我们自己也在违规先例名单里（曾自定 21 个 `--crm-*` 私有 token 写进设计规范）。
   单向拷问 = 甲方拍脑袋。
4. **原型优先纪律**（B 档增量与「长什么样」类问题的呈现方式）：
   **不许把候选增量以「要不要做 / 要不要排期？」的形式抛给决策者** —— 那等于要求对方
   **凭想象**做判断，答案必然飘（要么随口答应，要么随口否掉）。
   **正确做法：先出一版高保真原型，让对方看到再决定。**

   理由：人类看高保真原型的带宽远高于读文字选项。看到东西，一眼就知道要不要、哪里不对、
   少了什么；读一段描述，只能各自脑补出不同的画面，然后在评审会上才发现理解的不是一回事。
   **设计评审的最短路径是「看到」，不是「读到」。**

   ⚠️ 本项目实例：I3「服务项目维度订单看板」本以「要立需求排期吗？」提问，
   被需求方直接纠正 ——「**你应该说，我设计一版你先看看，用高保真原型给人类传达是最直接的。**」

   原型的三条硬要求（否则原型本身会误导人）：
   - **用宿主真实 token 渲染**，不自己配色。证据要从 `@appthen/vibe-workspace` 的
     构建产物里取（`--portal-*` 明暗两套 + shadcn 语义变量），否则评审看到的颜色不是最终颜色。
   - **显式标注「原型 · 示例数据」**。原型里必然是样例数字，不加标注就违反 §5.2 的 L3 纪律
     （会让人把示例值读成真实值）。
   - **附「待拍板项」清单**，把分歧点显式列出（形态选择 / 口径确认 / 未做项及其原因），
     让评审对着原型回答，而不是对着空白提问。

## 6. 角色边界（最容易搞错的一点）

- 我们站甲方位，管的是三件事：**合规**（是否守平台契约）、**可维护**（结构／成本／可回退）、
  **一致**（跨模块体验是否统一）。
- **但「产品意义」的判定权在业务方 / 最终用户，不在我们。**
- 平台以「大老板」自居去替业务方定义产品意义，产出会是**平台自嗨的扩展** ——
  好看、合规、跨模块一致，**但没人用**。
- 正确姿势：**我们负责「能不能、值不值、代价多大」，业务方负责「要不要」。**
  有分歧时，出证据 + 出选项 + 给出我们的建议，**但不替对方拍板**。

## 7. 通过与不通过

**通过条件**（全部满足）：

- [ ] **决策台账已通读**，且做了「**已拍板决策比对**」（逐条回答：有没有 D0xx 已经拍过它、拍的是做还是不做）
- [ ] **文档树已定位并读过**（`<域>/NN-*.md` 命中本功能的那几篇），且报告附「**条款对照表**」（结论 → `D0xx` / `NN §x.x`）
- [ ] **代码注释里的编号已逐个追到原文**；追不到的登记为「编号悬空」
- [ ] 已核对**文档状态级别**（第 2 级＝设计定稿但代码可能未实现），据此判断哪些是"设计"、哪些是"已存在"
- [ ] 三张清单齐备，且**每一条都带证据**（文件／行号／字段名／集合表达式）
- [ ] 已确认本功能的**主语属于本模块**（没有把别的模块的核心对象搬进来 —— 见 §2 第 0 问）
- [ ] C 档项已明确排除并**登记**（不是悄悄砍掉）
- [ ] 数据真实性三级验证齐备（L1 字段存在 / L2 有写入路径 / **L3 有真实数据填充**），或已列入缺口清单
- [ ] B 档增量需决策者拍板时，已附**高保真原型**（而非文字选项 —— 见 §5.4）
- [ ] 需求方对 A 档范围**明确点头**

**不通过**（不允许进入设计阶段）：
